# PROMPT PARA REPLIT AGENT — BACKEND MVP DE MEDIFLOW IA

## 1. Contexto del proyecto

Estoy desarrollando **MediFlow IA**, una plataforma de apoyo a la atención médica que permite registrar pacientes, gestionar consultas, generar informes clínicos asistidos por IA, realizar triaje, administrar la cola de atención y gestionar recursos médicos.

El frontend ya está desarrollado con React y TypeScript. También existen workflows de n8n para el procesamiento de consultas y el triaje de pacientes.

Necesito implementar la infraestructura básica del backend y conectar el frontend con una API real.

### Tecnologías obligatorias

- Backend: Python con FastAPI.
- Base de datos: PostgreSQL.
- ORM: SQLAlchemy 2.x.
- Migraciones: Alembic.
- Validación: Pydantic.
- Pruebas: pytest y HTTPX.
- Integración con IA: workflows existentes de n8n mediante HTTP.
- API: REST con JSON.
- Identificadores: UUID.

**No reemplaces el frontend ni cambies su diseño visual.** Trabaja sobre el proyecto existente, conserva sus componentes y funcionalidades actuales y adapta el backend a sus necesidades.

Campos mínimos:
- id
- full_name
- email
- password_hash

- is_active
- created_at

- sex

- created_at

Campos mínimos:
- id
- patient_id
- doctor_id
- status
- chief_complaint
- created_at
- updated_at
- confirmed_at

Una consulta debe estar vinculada a un paciente y, cuando corresponda, al profesional responsable.

Campos mínimos:

- consultation_id
- version
- report_data
- review_status

- confirmed_at

### TriageAssessments

Campos mínimos:

### ResourceAssignments

## 5. Implementar los endpoints REST

Utiliza el prefijo `/api`.

### Salud del servicio

- `GET /api/healthz`

Debe comprobar que la aplicación funciona y devolver un estado apropiado de la conexión a la base de datos sin exponer credenciales ni detalles internos.

### Autenticación

- `POST /api/auth/login`
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `GET /api/auth/me`

Implementa autenticación real, hash seguro de contraseñas, autorización por roles y protección de endpoints.

No almacenes contraseñas en texto plano ni expongas credenciales en el frontend.

### Pacientes

- `GET /api/patients`
- `POST /api/patients`
- `GET /api/patients/{patient_id}`
- `PATCH /api/patients/{patient_id}`
- `GET /api/patients/{patient_id}/consultations`

Incluye paginación, búsqueda y validación de datos.

### Consultas e informes

- `POST /api/consultations`
- `GET /api/consultations/{consultation_id}`
- `POST /api/consultations/{consultation_id}/process-report`
- `PATCH /api/consultations/{consultation_id}/report`
- `POST /api/consultations/{consultation_id}/confirm`
- `POST /api/consultations/{consultation_id}/vital-signs`

La generación de informes debe permitir revisar y corregir el resultado antes de confirmarlo.

### Triaje

- `POST /api/consultations/{consultation_id}/triage`
- `GET /api/triage/{assessment_id}`
- `POST /api/triage/{assessment_id}/review`

Valida y persiste los resultados devueltos por n8n.

No permitas que un cliente pueda modificar arbitrariamente la prioridad de un paciente sin autorización y sin un registro de auditoría.

### Cola de atención

- `GET /api/queue`
- `GET /api/queue/{entry_id}`
- `PATCH /api/queue/{entry_id}/status`

Permite consultar y actualizar la cola, con filtros por estado y prioridad.

No inventes reglas de orden clínico. La ordenación por prioridad debe depender de un protocolo aprobado y de las reglas de negocio configuradas.

### Recursos

- `GET /api/resources`
- `POST /api/resources`
- `GET /api/resources/{resource_id}`
- `PATCH /api/resources/{resource_id}`
- `DELETE /api/resources/{resource_id}`
- `POST /api/resources/{resource_id}/assignments`
- `POST /api/resource-assignments/{assignment_id}/release`

La eliminación de recursos debe ser lógica cuando existan referencias históricas. Impide asignaciones incompatibles con el estado o la capacidad del recurso.

### Dashboard

- `GET /api/dashboard/summary`

Devuelve estadísticas calculadas a partir de los datos reales de PostgreSQL, según los indicadores que ya presenta el frontend.

No inventes cantidades ni devuelvas valores fijos como si fueran datos reales.

## 6. Integración con n8n

Ya existen dos workflows. No construyas otros workflows ni reemplaces la lógica de IA existente.

### Workflow de consultas

Webhook existente:

`POST /webhook/mediflow/consultation`

El workflow recibe:
- sessionId
- doctorId
- patientId
- language
- transcript

La transcripción es temporal y debe procesarse sin guardarla permanentemente.

El workflow extrae información clínica, genera un informe estructurado y revisa el informe antes de devolverlo.

El backend debe:
1. Verificar que el usuario está autorizado para acceder a la consulta.
2. Validar el payload.
3. Enviar la información necesaria a n8n.
4. Validar la respuesta recibida.
5. Devolver el informe al frontend para su revisión.
6. Persistir la versión confirmada por el profesional mediante el endpoint correspondiente.

### Workflow de triaje

Webhook existente:

`POST /webhook/mediflow/triage`

El workflow recibe identificadores de sesión y paciente, motivo de consulta, síntomas, edad, sexo, duración, antecedentes, medicamentos, alergias y signos vitales, según los datos disponibles.

La respuesta contiene:
- sessionId
- patientId
- status
- triage.priority
- triage.redFlagsDetected
- triage.redFlags
- triage.chiefComplaint
- triage.relevantSymptoms
- triage.missingInformation
- triage.reason

Implementa un cliente HTTP reutilizable para n8n, con timeout, tratamiento de errores, validación de respuestas y configuración mediante variables de entorno.

No pongas URLs privadas, tokens ni secretos directamente en el código.

Las llamadas de integración deben realizarse desde FastAPI, nunca directamente desde el navegador.

Los nodos de callback de los workflows existentes están desactivados. Para esta primera versión, FastAPI debe invocar los webhooks y procesar sus respuestas de forma síncrona, evitando persistir dos veces el mismo resultado.

Si n8n no responde, devuelve un error controlado y conserva un estado recuperable. No inventes resultados ni marques una operación como completada cuando haya fallado.

## 8. Seguridad y privacidad

Implementa las siguientes medidas:

- Hash de contraseñas mediante Argon2id.
- Autenticación y autorización por endpoint.
- Protección de datos según el rol y el recurso.
- Variables de entorno para las credenciales.
- Validación estricta de entradas y respuestas de n8n.
- Límites de tamaño para las solicitudes.
- Timeouts y tratamiento de fallos de integración.
- Auditoría de operaciones relevantes.
- No almacenar la transcripción completa permanentemente.
- No devolver datos de depuración de n8n en producción.
- No incluir información clínica en mensajes de error o logs técnicos.
- Utilizar transacciones para las operaciones que deban actualizar varias entidades.
- Implementar idempotencia donde existan reintentos que puedan duplicar registros.

No habilites una configuración de seguridad ficticia. Si alguna medida no puede implementarse completamente en el entorno actual, documenta qué falta.
